# 共同架构：从模型调用到完整工作闭环

Agent 的架构可以先理解为一个分工明确的工作闭环：**模型依据当前资料选择动作，程序让动作真正发生，再把观察结果交回模型**。长任务、计划、多 Agent、记忆与恢复，都围绕这个闭环增加职责。不同实现的类名和拆分可以差别很大，读者先掌握这些职责，再学习各自怎样落地。

本章使用同一任务：“读取需求与 CSV 导出代码，修复字段转义，运行验证并说明结果。”读完应能手工推演一次请求，区分模型决策和程序推进，并把新的框架放进同一张职责地图。这里给出的是本书的**参考模型**，不是所有项目已经遵循的标准。

![共同运行主线是接纳目标、装配请求、模型决定、执行动作、保存观察与更新状态、判断继续或收口；存储、策略、扩展和观测贯穿相应职责](../assets/common-agent-reference.svg)


本章先把一次模型调用补成动作反馈循环，再解释为什么会话、资料、执行政策和恢复会成为独立职责。阅读时先沿 CSV 任务走完一次闭环；职责地图用来把这个闭环放回真实框架，最后才讨论架构表示与互补。

## 从一次模型调用开始：它少了什么

如果只把任务发给模型，模型可以解释 CSV 规则，甚至写出修改建议。但这次调用没有自动读取工作区，也没有替调用者改文件、运行验证。模型输出“请执行测试”与测试已经发生，是两种不同事实。

让人手工操作时，过程很容易理解：模型说需要读代码，人读取并把内容发回；模型提出修改，人完成后发回结果；模型再根据验证输出继续分析。Agent runtime 把中间的这些动作组织起来，让工具结果自动成为后续输入。

因此，工具反馈循环至少需要四项资料：

| 资料 | 在 CSV 任务中是什么 | 谁消费它 |
|---|---|---|
| 用户目标 | 修复转义、保持现有接口、运行验证 | 模型理解目标；宿主保留请求身份 |
| 当前消息 | 用户要求、以前的动作与工具观察 | 请求构建器与模型 |
| 工具定义 | 读取、修改、验证的名字、描述、参数契约 | 模型用它表达动作请求 |
| 工具实现 | 实际读文件、修改内容、运行验证的代码 | 程序按调用身份找到并执行 |

工具定义和实现可以由同一个对象提供，但职责不同。名字、说明与参数 schema 告诉模型可以请求什么；handler 才能产生效果。模型生成一个函数调用不会自行执行 Python 或 TypeScript 函数。

[Anthropic 的最小参考实现](https://github.com/anthropics/claude-quickstarts/blob/9ec32b91df50b0d4906cae64b13c6298055ff40d/agents/agent.py)把请求、调用提取、工具执行、结果加入历史放在一个循环里。这有助于理解最小分工；生产工作还需要在相应位置补充身份、控制、状态及执行政策。

## 手工走一遍反馈循环

先假定应用定义三个教学工具：read_source、apply_patch、run_checks。它们不是九个对象共有的实际工具名。执行器能找到这些工具，模型请求时能看见对应定义；用户目标已经作为消息保存。

### 第一轮：模型发现缺少事实

第一次请求包含用户目标、行为约定和工具定义，还没有导出源码。模型可能返回下面的调用节选：

```json
{
  "role": "assistant",
  "content": "先查看导出函数与已有验证。",
  "tool_calls": [{
    "id": "read-1", "name": "read_source",
    "arguments": {"path": "src/export.ts"}
  }]
}
```

程序不从“先查看”这句话里猜命令，而从结构化调用读取工具名与参数。它校验调用、找到 handler、执行读取，然后保存与 read-1 对应的结果。此刻得到的是**读取观察**，还没有修改文件。

```json
{
  "role": "tool",
  "call_id": "read-1",
  "content": "exportCsv 直接拼接字段；现有验证只覆盖普通字符串。"
}
```

这些字段是中立的教学表示，具体 provider 与框架的字段不同。共同要求是：模型动作与执行反馈要能关联，语义内容和控制字段要能分别解释。

### 第二轮：新观察改变下一动作

下一请求要包含原目标、read-1 调用和读取结果。只有保留观察，模型才能根据实际代码决定修改；如果仍只发送最初问题，它就没有获得刚才读取的新事实。

模型现在可能调用 apply_patch。执行器完成修改，返回受影响位置或具名失败。即使本轮的 assistant 正文写着“已经修复”，也要结合工具结果理解实际发生的动作。程序保存结果以后，模型才有材料判断是否继续验证。

### 第三轮及以后：验证也是观察

模型请求 run_checks，工具执行后返回结果。如果结果表明缺少换行覆盖，模型可以补充验证或调整实现，再次运行工具。若验证通过，它可以说明完成了哪些修改和检查。

| 请求前 | 此次新增事实 | 模型可作出的下一决定 |
|---|---|---|
| 首次请求 | 用户目标与工具能力 | 查资料、澄清或直接回答 |
| 读取以后 | 当前代码与已有验证 | 修改、继续读取或改变方案 |
| 修改以后 | 修改是否成功、影响位置 | 验证、追加修改或解释阻碍 |
| 验证以后 | 检查结果 | 修正、增加检查或收口 |

这是可变的任务轨迹，不是程序写死的四步。程序固定的是“请求—执行—反馈”的协作关系，模型选择的是这一轮具体做什么。同一轮也可能有多个工具请求，不能把一次用户工作、一次模型请求和一个工具调用算成同一种单位。

### 最小控制骨架

下面是教学伪代码，字段及函数由本章定义，未绑定真实模型或目标框架：

```python
messages = [user_request]
while True:
    request = build_request(messages, tool_definitions)
    response = model_call(request)
    messages.append(response)
    calls = response.tool_calls
    if not calls:
        return response.answer  # 本教学循环的正常结束；生产收口条件另讲。
    for call in calls:
        checked = validate_call(call, tool_definitions)
        result = execute_registered_handler(checked)
        messages.append(make_tool_result(call.id, result))
```

它展示最小闭环的因果关系：先有调用请求，再执行，再把关联结果反馈给下一请求。预算、取消、输入队列、hook、持久确认等没有在这段伪代码中展开，后文会把它们放回真正生效的边界；省略它们不是宣布生产系统可以无限循环。

[Hugging Face 的动作与观察课程](https://github.com/huggingface/agents-course/blob/3c469e773ec04e5f338b727ff20e3a6ea823ff81/units/en/unit1/agent-steps-and-structure.mdx)适合建立这个直觉。实际系统可能不公开模型的中间推理文字；可观察的工具请求、结果与程序状态，已经足以分析主线。

## 为什么最小循环会长成 harness

当需求增加，最小函数中原本挤在一起的职责需要明确边界。“增加机制”应当说明解决哪个实际问题，而不是把框架名称拼到循环外面。

| 新需求 | 最小循环缺少什么 | 需要明确的职责 |
|---|---|---|
| 同一会话接收后续输入 | 哪些历史和配置属于同一交互 | 会话身份与宿主生命周期 |
| 运行中补充要求 | 新输入何时能进入当前请求 | 队列、请求边界与继续控制 |
| 长工具结果不断积累 | 本次该保留哪些语义 | 历史、模型视图与上下文预算 |
| 修改、命令或远程 API 有效果 | 可见调用是否获准执行 | 参数受理、授权与执行环境 |
| 工作需要跨进程中断重建 | 光有聊天消息不知道推进位置 | 持久控制资料与恢复执行器 |
| 部分任务交给子执行者 | 子任务获得什么，父任务怎样等待 | 委派输入、结果、身份与归属 |
| 需要解释结果为什么可信 | 最后一句回答不足以说明过程 | 轨迹、验证事实与交付记录 |

harness 在本书中指这些运行配套机制：它组织模型怎样获得输入、动作怎样被执行、状态怎样推进，以及当前工作怎样被观察和控制。它可以采用一个进程内循环，也可以把控制写成图或持久 Task；不要求存在一个恰好叫 Harness 的类。

每项职责也不必单独占一个模块。小系统可以将几个职责放在同一个函数；长期服务会更明确地分开所有权与生命周期。理解职责以后，才能判断增加抽象是否有必要，或者已有模块是否已经承担了它。

## 建立一张能跨框架使用的职责地图

![产品宿主拥有入口和交互生命周期，运行控制组织请求与继续，模型及工具适配落实调用；历史、工作记录和模型投影提供不同数据，策略与观察分别作用于实际边界](../assets/common-agent-layers.svg)

这张图按**问题归属**分层，不按 import 路径或文件夹数量分层。模型也可以是远端服务；若一个远端服务接管整项 Agent 工作，接入方连接的是执行器，不再只是一个模型协议适配器。

### 产品宿主：一项工作从哪里来

CLI、编辑器、HTTP Gateway 或 SDK 接收用户输入，选择会话，准备资源与回调，把工作交给运行时，并把结果展示或投递给调用方。用户身份、交互会话和一次模型请求的生命周期不同；宿主决定资源什么时候构造、缓存或释放。

Pi 的 CLI/SDK 构造 AgentSession；DeerFlow Gateway 管 thread 与 run；Hermes 的 CLI、Gateway、ACP 决定 AIAgent 的生命周期。它们在不同产品里承担相近问题，却不能仅凭“都叫 session”认定身份与复用契约相同。

### 运行控制：这一项工作怎样继续

运行时准备请求，消费模型输出，安排工具批次，检查等待、队列、hook 和停止条件。规划可以由主模型在循环中完成，也可以组织独立的计划消费流程；程序必须知道谁负责下一步推进。

这里需要区分两个决定：**语义决定**是模型认为接下来应当做什么；**推进决定**是程序根据调用、状态、队列和策略，决定现在可以执行、等待、继续还是停止。模型准备回答，程序仍可能因待处理输入或结束 hook 要求继续；工具清单全部 completed，也仍可能需要业务验收。

### 能力与适配：谁把意图变成实际调用

模型适配器组织厂商协议、消息转换、流式响应与规范化；工具执行器处理 handler、参数和效果环境。MCP 可以把外部工具接入这个执行面，技能可以提供任务知识，hook 可以改变请求或执行行为。它们参与不同边界，不能统称为“插件调用”。

工具定义的发现、被加入当前请求、获得执行授权和实际产生效果是不同动作。有些系统在同一对象里提供这些能力，有些经过多个包装层；学习时追到终端 handler，才能确认谁真的执行了动作。

### 数据与状态：历史、工作、请求分别保存什么

原始历史回答“发生过什么”；工作状态回答“现在推进到哪里”；模型视图回答“本次看见什么”。长期记忆、知识库和产物可以提供额外资料，但不会自动成为当前请求，也不会自动代表正在执行的工作。

Pi 的历史树、DeepSeek 的事件与 surface、LangGraph 的 channels/checkpoint、Pico5 的 Entry/Task/Document，是对这些问题的不同组织。先问资料由谁生产、谁消费、何时生效，再解释具体类型名，就不会把所有内容压成一个 messages 数组。

### 横切职责：不另造一个平行 Agent

执行政策要放在参数和效果实际经过的位置；上下文选择要放在请求形成的位置；观测要区分流事件、提交事实与业务结果。它们会跨过主线的多个位置，但不因此成为另一个独立规划器。

例如 middleware 可能改变这一次模型请求，也可能返回状态 update。两者的影响范围不同；理解主线中的请求边界与状态边界之后，再看 hook 顺序才有意义。后面各专题会给出数据前后对照。

## 同一种工作模式，为什么会有不同架构

反馈机制的相似，不意味着各系统只是在给相同数组换名字。最影响工程选择的差异，是程序怎样表示控制位置，以及哪些资料能在中断后重建。

| 控制表示 | 一次读取结束后怎样继续 | 带来的理解重点 | 本书代表 |
|---|---|---|---|
| 进程内控制流 | 函数收到结果，回到下一请求边界 | 活跃调用栈、取消、队列与会话重建分开 | AgentSession、Codex core、Hermes 原生；Claude 冻结 query |
| 状态图与调度 | 节点返回 update，合并状态，再按边和任务调度 | state、reducer、超步、节点重跑与 checkpoint | LangChain 构图，LangGraph 执行，DeerFlow 装配产品策略 |
| 持久任务阶段 | 任务保存 checkpoint，等待子工作，按提交状态重新认领 | Task 身份、status/phase、事务及外部效果分开 | Pico5 |

这三种表示可以嵌套。图中的节点可以包含一个进程内工具循环；持久 Task 可以请求一个远端执行器。DeepSeek 的驱动主线仍是进程循环，同时用事件和 surface 组织资料；“事件历史”是数据表示维度，不应再当成与前三种互斥的执行策略。

相同任务下，读者要比较的是：如果程序停止，能够重新获得哪些事实、下一步由哪种控制资料决定、哪个效果需要独立确认。若需求只是恢复聊天历史，未必需要引入全部持久任务机制；若要延续正在进行的工作，单独保存回答文本又可能不够。

“架构长期可能接近”在这里是一种研究假设。更稳定的学习成果是：知道哪些职责需要被承担，以及职责之间应交接什么。未来项目换了类名或框架，读者仍能沿同一组问题理解它。

## 互补要看缺哪一项职责

最直接的真实组合是 LangChain 与 LangGraph：前者提供模型、消息、工具与标准 Agent 构图，后者推进图状态与任务。DeerFlow 再在上层装配产品 Prompt、middleware、工具、会话运行和投递。它们处于相互协作的层次，不能把三者当作互斥的“完整 Agent 框架”排名。[LangChain 构图](../frameworks/langchain/architecture.md)、[LangGraph 调度](../frameworks/langgraph/architecture.md)、[DeerFlow 装配](../agents/deerflow/architecture.md)。

如果另一个产品已经有成熟的宿主与投递能力，可以复用模型适配或执行器；如果应用需要恢复复杂状态，可以选择适合的控制表示。组合之前先写清谁拥有用户工作、谁保存历史、谁负责推进与终态，才能避免两层都认为对方负责收口。

| 选择问题 | 需要核对的接口 | 容易发生的职责重叠 |
|---|---|---|
| 换模型，保持原工作控制 | 请求和响应规范化；工具协议 | 不必要地重建整个 Agent 产品 |
| 增加知识检索 | 查询、Document、来源与请求注入 | 把检索器误当新的主循环 |
| 接入子 Agent | 子目标、上下文、结果与等待身份 | 父子两层重复决定同一计划项是否完成 |
| 增加持久执行 | 控制记录、当前代码、提交与效果边界 | 两套状态都宣称自己是推进事实源 |
| 增加产品 Gateway | 请求身份、执行归属、事件与结果接口 | 重复运行同一工作，或把断开读取等同取消 |

这些是设计检查问题，不表示任意两套框架已经有现成兼容接口。互补来自职责的合理组合；组合成本来自数据、生命周期、恢复和授权契约是否能对齐。

不足也应放到具体需求里判断。一个最小示例没有持久执行，可能只是为了教学；一个生产产品有很多包装层，也可能是因为宿主和效果边界真实存在。源码没找到某项能力与能力明确不受支持，需要分别说明。

## 按共同模型阅读各对象

后续阅读采用两个方向：横向专题先说明一种共用机制与设计选择；对象分册再解释谁在真实代码中承担它。每进入新对象，不必重新学习一整套孤立词汇。

完成下面的机制专题后，可以在[从 Agent 循环到业务系统](agent-in-business.md)把它们重新组合：模型如何开放求解，程序如何保存并推进工作，业务服务又依据什么确认完成。该篇承接设计取舍，本章继续负责解释最小闭环与共同职责。

| 共同问题 | 横向学习 | 实现中的定位方法 |
|---|---|---|
| 谁决定下一动作，谁负责推进 | [执行模式](execution-modes.md) | 找模型输出、计划消费、路由和停止条件 |
| 身份与对象怎样复用 | [所有权](ownership.md) | 找组合根、字段 owner、缓存和关闭 |
| 自然语言怎样进入下一请求 | [上下文与压缩](context-compaction.md) | 找历史、投影、请求副本和摘要采用 |
| 进行中的工作怎样保存 | [状态与恢复](state-recovery.md) | 找控制资料、提交点和恢复执行器 |
| 动作怎样走到效果 | [执行边界](execution.md) | 找 schema、handler、授权和执行环境 |
| 子执行者怎样协作 | [决策与委派](control-delegation.md) | 找委派输入、子生命周期、父等待和结果 |
| 完成由什么证明 | [观测与交付](observability-delivery.md) | 分开看消息、状态、工具结果、验收与投递 |

读完全部分册，应能够给一套新实现画职责关系，而不是依赖它恰好叫 Agent、Session 或 Task。若同名概念再次出现，先确定层次、owner、输入输出和生命周期，再判断它与已学概念的关系。

## 演算练习与参考解答

**练习一。** 一次模型响应请求 read_source 和 run_checks 两个工具。执行器只保存了读取结果，然后请求模型。还缺什么？

参考解答：需要解释 run_checks 是否执行及相应反馈，保留两个调用与结果的关联。具体协议可能要求完整批次或允许其他分段，但不能把未得到的验证结果当作已成功。模型下一轮的资料范围和动作配对应当有明确含义。

**练习二。** 在一个图节点里运行上面的 while 循环。它属于固定编排还是动态 Agent？

参考解答：分两层回答。外层图决定何时进入该节点及返回后去哪里；节点内部由模型按观察选择动作，是动态反馈循环。两个层次可以组合，不能给整个系统只贴一个互斥标签。

**练习三。** 在原循环中增加一次检索调用，结果加入 messages。是否已经增加持久恢复或独立 Planner？

参考解答：增加的是资料获取能力及反馈内容。若没有额外控制记录，就没有因此获得工作恢复；若没有计划产物被后续执行代码消费，也没有因此变成独立规划执行。

**练习四。** 已有 Agent runtime，再加一层 Gateway。哪些责任应当先对齐？

参考解答：先对齐工作身份与会话身份、接纳与执行归属、输入与结果、取消与终态、事件读取和持久记录。Gateway 可以改变接入与投递，但不应未经设计再启动第二份相同工作。

这些练习要求从资料与职责推出结果，不需要真实模型。进入对象分册以后，用其真实类型替换本章的教学名字，再检查哪些契约相同、哪些是特有选择。
