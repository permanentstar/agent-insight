# 如何阅读 Agent 调用链

复杂 Agent 源码容易让人迷失在嵌套概念中。有效的阅读方法是先确认对象的职责和生命周期，再沿输入、控制权与写入位置追踪执行。

![先理解对象关系和概念，再追一次输入的执行链与状态边界](../assets/book-map.svg)

## 每深入一层，重新定位

| 要问的问题 | 需要找到的源码 |
|---|---|
| 这个对象由谁创建、在哪里注入？ | 组合根、工厂、构造参数和接口绑定 |
| 谁拥有它，何时结束或复用？ | 字段持有者、缓存 key、close/release 与 scope |
| 上层传入什么，下层实际执行什么？ | caller/callee、输入输出类型、handler/provider |
| 哪一步改变了权威状态？ | 内存采用、数据库事务、append/commit/flush |
| 失败后从哪里继续？ | checkpoint、重试分支、取消资格与重放条件 |

自造术语需要先定含义。例如 Task 可能是持久工作记录，也可能只是一个异步调用；Session 可能保存历史，也可能同时持有活动运行。词典中的层次、所有者和持久性，比类名是否相似更有判断价值。

## 沿主链路建立全貌

一次输入通常经过接入、上下文准备、模型请求、工具执行、结果回填和结束判断。先走通这条主线，再研究提前结束、错误、取消和恢复，才能知道某个边界影响了哪一段工作。

状态表补充每条转移的条件与结果；关系图帮助定位组件和走向。深入小节时持续记录“当前位置、调用它的上层、它进入的下层、状态与副作用归属”，不要从函数清单直接跳入底层状态机。

## 用正文代码保持阅读位置

每处关键代码先说明当前属于哪一步，再交代输入与输出。短节选保留真实符号和顺序，流程骨架注明省略范围，教学案例则明确其字段是应用定义。先在正文读出交接，再按需点开固定源码，避免跳进长函数后失去前一层的问题。

例如看到 `model_.invoke(messages)`，先问 messages 是由 state 还是当前 request 取得，system 何时加入，响应又由谁变成状态更新。随后查看上层 ModelRequest 与下层 Partner；这样既能追到最终调用，也能回到原来的模型—工具反馈位置。

回到主线时，用一句话复述“本步接收什么、生成什么、交给谁”。若无法从段落、图和代码得出答案，先记录缺失的交接，继续读下层函数不会自动补齐它。[LangChain 的完整请求交接](../frameworks/langchain/architecture.md)提供对应例子。

## 按证据判断结论

| 依据 | 可以说明什么 | 仍需另外证明什么 |
|---|---|---|
| 源码调用与写入 | 已存在的分支、字段、顺序和控制点 | 实际效果、性能与所有配置组合 |
| 从状态约束推导 | 特定条件下的行为与风险 | 作者动机和线上部署事实 |
| 官方设计与接口说明 | 预期契约和能力边界 | 实现是否完整符合设计 |
| 历史架构研究 | 相应材料描述的机制 | 当前产品行为 |
| 设计建议 | 某场景下可采用的方案及代价 | 系统已经实现该方案 |

“事件已显示”“记录已持久”“外部动作已完成”是不同判断。比较恢复或交付能力时，分别找到每种判断的证据。
