# 书籍写作与教学评审规范

本书面向有基础编程知识、正在学习 Agent 实现的读者。正文要让读者建立完整设计认知，能够沿任务解释对象、状态和数据如何协作。这份规范适用于后续新增及修订的对象分册、机制专题和横向比较；具体研究问题由 templates/ 中的三类模板组织。

本页是写作和教学评审要求的统一依据。AGENTS.md 提供代理入口，[contracts.md](contracts.md) 管理证据与元数据，[update.md](update.md) 记录修订范围和验证结果。批注原文及处理状态保存在 gitignored 的 `.review/`，可复用的写作要求归入本页。

## 读者与全书主线

正文直接讲 Agent 的工作方式、真实实现和设计取舍。资料整理过程、迁移说明和维护进度留在维护文档；版本及研究范围集中在开篇版本说明，正文只在解释机制差异确有需要时交代适用条件。

先用共同职责建立认知，再定位各对象的实际实现：输入接纳、请求组织、模型决策、动作执行、观察与状态更新、继续及收口。各框架的具体对象、控制表示与持久性按源码解释。长期架构趋同是研究假设；比较要说明真实共性、各自特点、互补条件与不足。

学习内容应覆盖重要分层、状态与转换、执行模式，以及两类非结构化问题：自然语言资料如何组织，模型如何根据资料动态选择后续动作。ReAct、Plan & Execute、产品 Plan Mode、Todo、子 Agent 拓扑和持久运行分别定位；支持程度沿实际入口与执行链路说明。

## 每章先给全程，再沿步骤展开

开篇先解释场景和机制用途，用读者已经能理解的词表达结论，再给全章流程图和步骤概览。读者在进入细节前应知道过程从哪里开始、经过哪些阶段、到哪里结束。

主体按执行顺序或明确的学习依赖展开。每个重要步骤单独成节，开头承接上一步的产出，正文解释该步骤的处理，末尾交代结果由谁采用。同一层保持一致的抽象粒度，进入下层时说明调用者交出了什么、下层承担什么。

| 小节需要回答 | 应交代的内容 |
|---|---|
| 当前在哪一步？ | 对应总图位置、所属对象与职责 |
| 为什么现在做？ | 前一步留下的问题或准备好的资料 |
| 输入从哪里来？ | 调用者、对象／状态起点与关键字段 |
| 本步怎样推进？ | 主要动作、状态变化、控制条件或模型选择 |
| 输出交给谁？ | 下一消费者、采用时机与后续走向 |

一个功能若贯穿多个步骤，先让主流程闭合，再单独串讲它与各步骤的交点。例如内容编辑既影响摘要输入，也影响请求投影；应分别定位这两处作用。事件写入等贯穿流程的旁路，在总图中画为侧路，正文集中解释，保持真实发生顺序。

每段围绕一个判断或事实展开，并交代它与当前问题的关系。段落衔接靠输入、结果或因果关系建立，避免只用“再看一个细节”接上新的局部实现。章节之间也应说明上一章准备了什么、本章继续解决什么。

## 概念先解释用途，再进入实现

新概念首次出现时，先用一句白话说明它是什么、解决什么问题，随后解释其所在层及与已有对象的关系。专业名称保留上游原词，中文表达沿用项目定名。自造或嵌套较深的概念可先放入词典，流程中仍要给出必要的定位。

介绍对象时交代所有者、构造或注入方式、作用域和生命周期。讲 reload、切换或恢复时，先说明哪些对象沿用、哪些资料重读、哪些对象重建，再按需展开代码。结论应建立在已解释的概念上，避免先抛权限、恢复或持久性判断，让读者自行补齐对象含义。

只引入当前解释需要的相邻概念。直接陈述事实和适用条件，减少“不是 X，而是 Y”、无关机制对比和重复的否定说明。确需区分容易混淆的对象时，说明各自承担的职责与实际交接。

## 先讲操作意图，再给源码对照

流程节点、步骤说明和状态转换的主句先说“这一步要解决什么、完成后谁能继续”，再把状态名、字段赋值、函数和源码位置放入括号、对照列或紧随其后的实现说明。读者应先理解操作顺序与效果，再按需核对代码；不能要求读者从变量变化反推用途。

例如重试不要只写“Task → sleeping，checkpoint.phase=retry，保存 until / attempt”。应先写“记住下次尝试时点，结束本次执行占用；到期再准备请求”，随后补“（sleeping/retry；until / attempt）”。恢复、取消、队列接纳和任务交接同样要说明保存这些资料之后，运行能如何继续。

这里的意图指当前操作在执行链上的用途，依据输入、控制流和后续消费者解释；作者未说明的设计动机仍要标为推断。字段表、状态名、数据样例和源码块保留真实名称，前文先交代它们服务的工作。图中空间有限时，优先留完整动作与交接，把字段明细放到图后对照表。

## 用图、案例和关键代码共同解释主线

讲分层、流程、时序、状态变化和模块协作时先给图。图应标出实际组件、状态或字段、输入输出、继续及终点；局部图要能回到章节总图。显式状态机按真实状态绘制，条件循环按真实控制流绘制。

图示使用仓库内可编辑 SVG，自带不透明画布及显式颜色，附准确 alt 文本，并在实际页面的浅色和深色主题中检查。表格补充转换条件、字段或对象对应，图后文字解释处理原因和数据采用。

每个机制用一项正常任务贯穿。给出已知输入、对象／状态起点、更新规则、结果和下一消费者，让读者能演算下一请求或状态。改变 leaf、配置、模型选择或时间点前先说明新条件；图、表、代码和案例始终使用一致的身份及顺序。

引用源码时，正文内给出对应的关键调用路径、短源码节选或流程骨架，供读者一眼看到主要步骤。固定 GitHub 链接放在对应说明旁，注明它支撑什么，供按需查阅完整实现。源码链接与函数名清单只承担追溯作用。

代码材料明确区分源码节选、按源码整理的流程骨架、候选设计伪代码和教学数据。保留真实符号与执行顺序，显式标明省略范围。书中的新增阅读注释使用中文，解释职责、数据交接、采用时机及省略目的；引用的上游标识和错误文本保持原样。

简单遍历等局部细节选择性展开，先说明它插在主流程哪一步。介绍 hook 时，先用同一时间线标出各入口，再解释每类返回值怎样被采用；相同遍历方式下的接管、变换、通知和继续判断仍按各自契约说明。

## 深度围绕学习问题组织

章节深度以读者能复盘机制、推导结果和解释取舍判断。重要状态、流程、数据变化与层次需要展开，不能用术语表、导览或简短矩阵代替。已有材料中的有效案例和独有机制继续保留。

正常主线先讲完整，影响主线理解的重要分支随后解释。细碎异常组合、边界 case 和简单实现细节按需放入补充或折叠段落。拆章看学习问题和前置知识，篇幅及源码函数数量不作为拆分依据。

横向比较先解释共同问题和代表机制，再用同一任务呈现实现差异，最后汇总取舍。收益和不足给出适用条件与证据，架构互补要交代输入输出、所有者及恢复契约怎样衔接。

跨框架的设计归纳放在横向专题之后、对象分册之前，以设计问题组织，使用多个实现交叉检验。对象自身的演化篇保留机制、代码与取舍，双方通过链接衔接，不重复整段结论。归纳要区分开放模型决策、运行控制和业务事实；同一职责可由不同控制表示承担，不把 durable 或其他单一方案设为全书演进终点。作者明确目标、本书工程判断和行业趋势假设分别表达。

## 教学评审必须检查主脉络

修订前读取 `.review/annotations.json`，结合摘录、章节与 sourceHash 核对意见。代表性意见应覆盖用户指定范围内的所有相关章节，处理范围在维护记录中说明。后续通用要求按本页执行；已有正文的批量改写继续遵守用户当次范围。

评审者优先检查阅读过程中是否始终知道“当前在哪一步，输入从哪里来，结果交给谁”。评审需要指出具体阅读断点和缺失的前提，检查以下问题：

| 检查问题 | 可接受的结果 |
|---|---|
| 只读开篇和总图，能否说出整章过程？ | 起点、主要阶段与终点明确 |
| 从一个小节进入下一节，是否需要作者额外解释？ | 前置资料和因果／时序承接已在正文交代 |
| 新术语出现时，是否已知道其用途与层次？ | 概念说明先于依赖它的实现结论 |
| 能否用给定案例推导结果？ | 输入、更新规则、采用时机和参考解答完整 |
| 图、代码和案例能否相互核对？ | 对象、字段、分支、时间点与来源一致 |
| 暂时遮住括号内的代码，能否复述操作意图和交接？ | 主句说明要解决的问题、产生的效果和后续消费者，字段用于核对 |
| 源码细节是否帮助理解当前步骤？ | 细节有明确位置，主要过程不被旁枝打断 |

独立读者检查时提供文档与学习问题，重点检验主线复述、上下文衔接和正常案例推导。源码核验、结构检查和构建分别报告；读者检查通过只说明所检查的学习问题已接通。

每条已处理批注保留原文，通过本地审稿机制更新状态。原始批注不进入 Git 或公开构建；本页只保存可复用要求。后续发现新的通用写作要求时，就地更新本页，并同步相关模板的引用。
